6. **Task [Extended] - Audio level simulation and AudioLevel driver**: Simulated the analog front end, chose the on/off rules with the owner, moved audio sensing into a driver class<br>
   **Result**: Star Colonel asked for hysteresis so audio switches off only 1 sigma below the threshold, then for a driver class and a simulation before deciding. `notebooks/frontend_model.py` models the Mk10 schematic: LM324A gain 101 above 159 Hz around VGND 0.88 V (47k/10k, while the note says VCC/2), precision rectifier biased by R4 1 MΩ to GND, peak detector 10 ms attack and 1 s decay, ADC every 51 ms. `notebooks/audio-level-simulation.ipynb` shows quiet reads 4-35 counts (U1.2 bias current through R4 plus hum; 67 with a 3 mV ground loop) and music saturates at 575-580 from -40 dBFS; threshold 300 is -47 dBFS. Learning samples on music therefore spread 0-7 counts, so a 1-sigma band does nothing, and learning to the mean set a threshold the same music could not exceed (DEF-LEARN-16). A Python replica of the firmware decisions, matched to simavr within 0.30 s, scored 6 designs over 15 cases: off at T minus sigma 7/15, off at 25% of T 11/15, simple 14/15, quiet-based 15/15. Owner chose the whole-driver scope; the simple design went in as the base of both options: `src/AudioLevel.h/.cpp` samples in every state from `loop()`, clears the average on idle entry and waits for 50 new samples (fixing DEF-SENSE-13-1, START after standby from a stale average), holds audio on above threshold/4, learns half the average with a 160 minimum. Also fixed the settling check after the `millis()` wrap (DEF-TIMING-17). Sigma criteria rejected; EEPROM bytes 14-15 stay unused. Explainer page https://claude.ai/artifact/3GrEjr8zMGctp6QpvrqmnZ. Circuit findings for the owner: U1.2 input driven below ground, quiet set by bias current through 1 MΩ, stale ADC_REF 3V3 note. JupyterLab autosave once overwrote the executed notebook; reload from disk before saving.

11. **Task [Extended] - EEPROM recovery for a board without the eeprom commands**: Added the temporary bridge firmware and the automatic flash save and restore flow<br>
    **Result**: The deployed board runs firmware that predates `eeprom dump` and `eeprom write`, so the backup had no path to the stored codes. Every git revision that stored a threshold uses the same layout, bytes 0-5 START, 6-11 STOP and 12-13 threshold; only revisions before `10d3c8d` stored one code and no threshold. `tools/eeprom-bridge` is a separate PlatformIO project whose sketch serves only `help`, `eeprom dump` and `eeprom write`, never writes the EEPROM on boot and needs 3028 bytes of flash. When the first dump is unanswered, `tools/eeprom_tool.py backup --bridge` saves the whole flash to `eeprom.firmware.hex` through PlatformIO's avrdude at 57600 baud, flashes the bridge, dumps the EEPROM, writes the saved image back with `-D` and verifies the read-back; the image is reused, and a re-run that finds the bridge banner writes it back without flashing again, so an interrupted run restores the same firmware. `decode_image` adds `threshold_set`, false for an erased 0xFFFF. Four simavr bridge tests use a new `firmware` argument on `sim.Board`; six host unit tests cover the avrdude command, the restore order, image reuse, a re-run that finishes a failed restore and the missing `--bridge` error. `make test` 100 passed, both firmwares 0 warnings, main firmware 24378 bytes flash and 1061 bytes RAM. ACC-EEPROM-65 added and logged; the live board run waits for the board.
